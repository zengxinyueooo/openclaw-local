## OPX Token 自动化获取优化

### 背景
用户希望实现完全自动化的 OPX Token 获取，无需手动操作。

### 尝试的方案

#### 方案 1: Chrome DevTools Protocol (CDP)
- 通过 `http://127.0.0.1:9222/json` 获取页面列表
- 使用 WebSocket 连接页面获取网络请求
- **问题**: macOS 系统安全策略可能拦截 HTTP 请求

#### 方案 2: 自动启动 Chrome
- 检测是否已有 Chrome 运行
- 使用 `open -na` 或 `spawn` 启动带调试端口的 Chrome
- **问题**: 当 Chrome 已在运行时，新实例无法启用调试端口
- `open -na` 会复用现有实例，忽略 `--remote-debugging-port` 参数

#### 方案 3: Browser Relay
- 使用 OpenClaw Browser Relay 扩展
- **问题**: 需要扩展已连接，当前未连接

### 当前状态
- 创建了 `get-token-auto.js` 自动脚本
- 脚本可以检测 Chrome 状态并尝试启动
- 核心问题: macOS 上已有 Chrome 运行时，调试端口启动困难

### 待决策
需要用户选择方案:
- A: 全自动但会重启 Chrome (推荐)
- B: 使用 Browser Relay (需要扩展)
- C: 手动启动一次，之后自动

## AppleScript 方案尝试

### 进展
- 用户已开启 Chrome 的"允许 Apple 事件中的 JavaScript"选项
- 创建了 `get-token.sh` 脚本，使用 AppleScript 与 Chrome 交互
- 脚本可以成功获取 Cookie

### 遇到的问题
- AppleScript 执行 `execute javascript` 时卡住/超时
- `timeout 30` 后返回空结果
- 可能原因:
  1. Chrome 无响应
  2. JS 执行超时 (fetch 请求)
  3. 权限问题
  4. 页面状态问题

### 当前方案对比

| 方案 | 状态 | 问题 |
|-----|------|------|
| CDP (9222端口) | ❌ | macOS 安全策略拦截 |
| 自动启动 Chrome | ❌ | 已有实例时无法启用调试端口 |
| Browser Relay | ❌ | 页面导航到 about:blank |
| AppleScript | ⚠️ | 执行 JS 时卡住 |

### 待决策
需要用户选择:
- A: 重启 Chrome 启用调试端口 (最稳定)
- B: 手动提供 token 一次，后续自动
- C: 继续调试 AppleScript
